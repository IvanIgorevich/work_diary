# Рабочий дневник

Учёт рабочего времени и отчётность: выгрузка трекера → рабочий дневник → документ, чат и таблица времени.

Общие правила для Codex и Claude — в `AGENTS.md`. Claude читает их через
`CLAUDE.md` и навык `/report`; Codex — как инструкции проекта. Новые
указания пользователя сохраняются здесь же, в проекте.

## Как пользоваться

1. Время ведётся в трекере. Работа — группа `Ruby › Работа › Domcap`: «А портал» — пункт а) плана дня,
   «Б портал» — пункт б) и т. д., плюс «Отчётность», «Связь портал», «Документация».
   Номер задачи можно написать в комментарии записи (`#7386`) — он важнее буквы.
2. Выгрузку из трекера скачать (Telegram складывает её в `~/Downloads/Telegram Lite/`) или положить в `inbox/`.
3. Дальше:

```
bin/report                     новые выгрузки → журнал, планы, сводка по дням и отклонение от цели
bin/report telegram            «План — Итог» по неотправленным дням одним сообщением для чата
bin/report telegram --plan-today   то же и в конце план на сегодня (без итога)
bin/report sheet               внести дни в таблицу времени (новый месяц создаётся сам)
bin/report month [ГГГГ-ММ]     ежемесячный отчёт (по умолчанию — за прошлый месяц)
bin/report push                коммит и пуш дневника
bin/report summary С ПО        часы по задачам за период и всего
bin/report db                  пересобрать SQLite-базу для запросов и анализа
bin/report backfill-records    дополнить прежние ежедневные records/*.txt
```

Фактический итог сегодняшнего дня не обрабатывается, пока день не закончится
(`--today`, чтобы включить). План на сегодня сохраняется отдельно без итога.
В Claude Code то же самое делает `/report`.

План дня, если его нет, составляется сам: задачи — по веткам и коммитам в `~/Work/Portal.Domcap`
(подзадачи сворачиваются по `data/tasks.yml`), остальные пункты — как в предыдущем плане.
Такой план помечен `auto: true` в `data/days.yml`, его можно поправить руками.
Созвоны («связь с командой») включаются в план только по понедельникам
и пятницам; дни заданы в `plan.scheduled_items` как номера ISO-дней недели.
Если связь была в другой день, её фактическое время всё равно попадает
в итог из трекера.

Отчёт за период состоит из последовательных пар «План — Итог» по каждому
дню. После них может идти план на текущий день без итога.
В сообщение для чата попадают только ещё не отправленные части:
если план первого дня уже опубликован, сообщение начинается с его итога.
В локальном дневнике остаются полные пары.

## Четыре части отчётности

| Часть | Содержание | Когда считать выполненной |
|---|---|---|
| Документ «Отчёты» | Планы, итоги, месячные отчёты | После проверенной записи; отметка `document` |
| Рабочий чат | Те же пары «План — Итог» | После фактической отправки; отметка `sent` |
| Таблица времени | Приход, уход, перерывы, часы | После проверенной записи; отметка `sheet` |
| Рабочий дневник | Рабочие записи, планы, текстовый журнал и SQLite | После локального сохранения и пересборки |

Сначала отчёты и часы показываются пользователю на утверждение.
Документ, таблица, отправка в чат и push — только после ясного указания
на русском языке. Локальные данные и черновики можно подготовить заранее.

## Что где лежит

| | |
|---|---|
| `data/work_log.csv` | все рабочие часы: отрезки из трекера, итоги дня из старого дневника |
| `data/days.yml` | план на каждый день и отметки документа (`document`), таблицы (`sheet`) и чата (`sent`) |
| `data/tasks.yml` | подзадача → задача, которую указываю в отчётах |
| `data/telegram_reports.csv` | мои «План/Итог на день» из рабочего чата с 2023 года |
| `journal/ГГГГ-ММ.md` | планы и итоги по дням, как они ушли в чат (собирается сам) |
| `config.yml` | цель часов в месяц, разбор трекера, шаблон месячного отчёта |
| `private/` | вне git: сырые выгрузки трекера, экспорт чата, ключ Google, `config.yml` с таблицей |
| `records/` | прежний дневник с ежедневным временем и накоплением по задачам; старые архивы плюс новые производные записи |
| `private/work_diary.sqlite3` | производная база: отрезки в секундах, планы, задачи, тексты чата и статусы четырёх частей |

CSV и YAML уже хранят данные в пригодном для обработки виде. Они остаются
источниками данных и сохраняются в git. Текстовые `records/*.txt`
сохраняются и дополняются для каждого завершённого дня, а `journal/*.md`
собирается из данных в формате «План — Итог».

При сохранении автоматически дополняются все завершённые рабочие дни,
начиная с первой управляемой даты в `data/days.yml`. Команда
`bin/report backfill-records` делает то же отдельно, не меняя CSV/YAML.
Как прежде, имя файла — следующий день, рабочая дата указана внутри:
например, работа за 21.09.2026 хранится в `records/2026-09-22.txt`.
Существующие архивы остаются дословно, время их сохранения не выдумывается.

Новые записи сохраняют все фактические работы и точные секунды:
`1) #6077, this day 4h 54m 19s, total ...`. `total` — накопленное
учтённое время задачи по рабочую дату включительно; для отчётности,
связи и документации пишется `total recorded`, потому что старые архивы
могли не содержать эти категории. Неразобранные пункты сохраняются
с `?`, пока их связь с задачей не выяснена. Производные файлы помечены
служебной строкой и пересобираются из источников; `migrate-records`
их игнорирует. Архивные строки также не мигрируются поверх дат,
уже покрытых более точными данными трекера/CSV, поэтому часы не дублируются.

SQLite добавлена для выборок по датам, задачам и состоянию отчётности.
База пересобирается при сохранении дневника и командой `bin/report db`;
её можно восстановить из CSV/YAML. Она хранится локально вне git, чтобы
не коммитить бинарный файл и не создавать второй независимый источник
правды. Правки вносятся в исходные данные, после чего обновляются и
текст, и база.

В базе есть таблицы `work_entries`, `days`, `plan_items`, `task_parents`,
`telegram_reports`, `reporting_statuses` и сводное представление
`report_totals`. Длительности хранятся целыми секундами; у дня без
фактических записей часы остаются неопределёнными, а не нулевыми.
Статусы: `done` — выполнено, `partial` — есть только часть,
`pending` — ожидает выполнения, `unknown` — исторических сведений нет.

Наличие архивной копии CSV не означает, что её данные уже сохранены.
Успешные импорты отмечаются отдельно в `private/imported_exports.yml`
после сохранения дневника; повторный импорт не дублирует часы.

Репозиторий публичный. Из выгрузки трекера сохраняются только рабочие записи, из чата — только мои отчёты
текстом; всё остальное лежит в `private/`.

## Доступ к таблице времени

Нужен сервисный аккаунт Google с правом «Редактор» на таблицу:

1. [console.cloud.google.com](https://console.cloud.google.com) → новый проект → включить Google Sheets API.
2. IAM → Service Accounts → создать аккаунт → Keys → Add key → JSON. Файл положить в `private/google-key.json`.
3. Открыть доступ к таблице на email аккаунта (`...@....iam.gserviceaccount.com`) как редактору.
4. `cp config.private.example.yml private/config.yml` и вписать id таблицы.

Gems: `bundle install` (нужен только `googleauth`, для таблицы). Тесты: `rspec`.

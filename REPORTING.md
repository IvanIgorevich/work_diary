# Порядок заполнения рабочей отчётности

Инструкция для Codex и Claude: от новой выгрузки до проверенных записей
в документе, чате, таблицах и дневнике. Общие правила и подтверждения —
в [AGENTS.md](AGENTS.md), команды и устройство проекта — в [README.md](README.md).

## Выгрузка и проверка часов

1. Новые CSV из браузера, ВКонтакте и других приложений складывать в
   `inbox/`, не в корень проекта. Также автоматически проверяются папки
   Telegram из `tracker.exports` в `config.yml`.
2. Установить, какой файл последний: проверить содержимое, период и SHA-256,
   а не только имя или дату скачивания. Учитывать исправленные копии с `(2)`
   и похожими суффиксами. Ошибочную выгрузку повторно не импортировать.
3. Проверить полностью покрытые даты, рабочие отрезки, переходы через
   полночь, пересечения и подозрительно длинные таймеры. Не исправлять
   неоднозначные часы без уточнения пользователя. Секундные пересечения
   не вычитать молча: сохранять источник и фиксировать расхождение.
4. Обрабатывать завершённые дни. Сегодня готовить только план, если
   пользователь отдельно не попросил сегодняшний факт. Наличие утренних
   записей в CSV ещё не означает, что сегодняшний день завершён.
5. `bin/report` импортирует и сохраняет локальные данные. Это не команда
   только для просмотра. Архив исходной CSV сохраняется в `private/tracker/`;
   успешный импорт отмечается в `private/imported_exports.yml` после сохранения.

Рабочая группа — `Ruby / Работа / Domcap`. Личные записи остаются только
в исходной выгрузке вне Git. CSV после повторного сохранения может содержать
разделитель из пустых полей: сводка после него не является рабочими отрезками.

Если пользователь уточнил ошибочный таймер без новой выгрузки, исходный
файл не менять. В `private/tracker_corrections.yml` записать точные исключения:

```yaml
exports:
  SHA256_ФАЙЛА:
    exclude:
      - date: 'YYYY-MM-DD'
        start: 'HH:MM:SS'
        end: 'HH:MM:SS'
        activity: 'Название ошибочной рабочей категории'
```

Переход через полночь исключается отдельными частями каждого дня; конец
предыдущего дня — `24:00:00`. Повторный импорт должен сохранять исправление.
Причины, содержащие сведения о личной жизни, в публичные файлы не переносить.

## Задачи и планы по дням

- Проверить Git и reflog в `../Portal.Domcap`, время пересчитывать по epoch
  в `Europe/Samara`. Учитывать ветку на начало дня, переключения и коммиты
  внутри рабочих отрезков. Открытая ветка сама по себе не доказывает задачу.
- `А портал`, `Б портал` и далее относятся к пунктам плана; номер `#...`
  в комментарии CSV имеет приоритет. При конфликте букв, Git и известных
  планов уточнить задачу. Согласованную разбивку сохранить в `data/days.yml`.
- В пункте а) основного плана — #7208. Другие задачи добавлять отдельно.
  Подзадачи сворачивать только по проверенным связям из `data/tasks.yml`.
  Номер новой задачи или её родителя не угадывать.
- В `git:` сохранять исходные номера задач дня, в `assign:` — интервалы
  назначения времени. Интервалы ограничивать реальными А/Б/В-отрезками:
  текущая реализация `assign` действует на любую попавшую внутрь активность,
  поэтому широкое правило может ошибочно забрать отчётность или созвон.
- Пункт «связь с командой» включать в план только в понедельник и пятницу.
  Фактическую связь в другие дни всё равно включать в итог по трекеру.
- План на сегодня сохранить отдельно: `bin/report` сам заполняет планы
  только для завершённых рабочих дат. Автоматические планы проверить вручную.

`GitActivity` — подсказка, а не готовое распределение времени. В частности,
ветка `hotfix/1234-name` распознаётся, а `hotfix-1234-name` может не распознаться.

## Дневник и сообщение для чата

Полный журнал содержит последовательные пары «План на день — Итог на день».
После завершённых дней идёт план на сегодня без сегодняшнего итога.

Перед подготовкой сообщения выяснить, чем заканчивается рабочий чат:
`sent` в `data/days.yml` означает отправленный день, `sent_parts: [plan]` —
только отправленный план. Обновлять эти отметки по фактической отправке
или подтверждению пользователя. Уже отправленные части не повторять.

`bin/report telegram --plan-today` печатает текст, но не отправляет его.
`--plan-today` добавляет только уже сохранённый план. Если завершённых
неотправленных дней нет, текущий CLI выходит раньше: план нужно получить
отдельно. Текст пользователю выдавать целиком в блоке для копирования.

Сохраняются одновременно:

| Формат | Содержание |
| --- | --- |
| `data/work_log.csv`, `data/days.yml` | Канонические рабочие часы, планы, назначения и отметки |
| `journal/*.md` | Полные планы и итоги, включая отчётность, связь и остальные рабочие категории |
| `records/*.txt` | Только номера задач, время за день и накопленное время по задаче |
| `private/work_diary.sqlite3` | Пересоздаваемая база для анализа |

Имя старого ежедневного файла — следующий день после работы; рабочая дата
указана внутри. Восстанавливать все пропущенные завершённые дни, сохраняя
ручные архивы. Производные файлы отмечены в `data/records_generated.yml`
и не должны повторно добавлять часы при миграции. Для анализа по задачам
использовать `report_totals`: оно учитывает `assign`; `work_entries` хранит
исходные отрезки. Журнал и БД отдельно от CSV/YAML не редактировать.

## Таблица времени и документ

Перед внешней записью подготовить изменения и проверить, что пользователь
уже дал ясное русское разрешение на эти действия. Повторно запрашивать
разрешение на уже согласованные шаги не нужно. `--yes`, ответы терминалу
и случайные «y/ok» разрешением не являются.

Перед изменением сохранить полную копию файла в `private/backups/`.
После записи прочитать результат заново; отсутствие ошибки API недостаточно.

**Таблица времени:** найти строку по полной дате в правильном месяце и году.
Записать C — приход, D — уход, F — перерыв; E считает формула `D-C-F`.
Перерыв равен промежутку от прихода до ухода минус фактические рабочие часы.
Проверить секунды, формулы дня, недельные и месячные итоги и соседние дни.
Новый месяц создавать по прежнему образцу. Его будущие дни заполнены
нормой, поэтому строка «ИТОГИ» до завершения месяца не равна факту.

`bin/report sheet` пропускает дни без времени прихода. Явные `--from/--to`
могут включить уже заполненные строки. Сам CLI не выполняет контрольное
чтение после записи — его нужно сделать отдельно.

**Документ «Отчёты»:** найти последний раздел нужного года. Существующий
план исправить, итог вставить после него; новые дни добавить по порядку.
Не дублировать даты и не заменять весь документ. Месячный отчёт поставить
после последнего дня закрытого месяца и перед планом на первое число нового.
После записи сверить текст, порядок и сохранность прежних разделов.

Отдельной команды для ежедневного обновления Google Docs сейчас нет.
`ReportsDoc` умеет вставку и поиск места для месячного отчёта. Если Docs API
недоступен, использовать разрешённый браузерный путь, сохранив копию и
проверив результат; доступы и настройки проекта Google самостоятельно не менять.

## Закрытие месяца и зарплатная таблица

Закрывать месяц только после импорта всех его дней. Сумма точных секунд
в дневнике должна совпасть с фактическим месячным итогом таблицы времени.
Не брать итог, пока последний день всё ещё содержит шаблонную норму.

`bin/report month YYYY-MM` не является чистым черновиком: при доступной
таблице он предлагает заполнить зарплату и документ. Не запускать его
с `--yes`, пока не проверены месяц, суммы и разрешение пользователя.

### Строка зарплаты

1. Найти «за <месяц>» и проверить год по соседним датам. `Salary.row(month)`
   выбирает последнюю такую строку без учёта года — слепо полагаться на неё нельзя.
2. Итог месяца округлить **вверх до четверти часа**:
   `ceil(секунды / 900.0) / 4.0`. Не округлять вниз и не менять фактические часы
   в дневнике и таблице времени из-за зарплатного округления.
3. В A поставить дату заполнения, в C — округлённые часы. Ставку и формулу
   суммы E сохранить; формат даты взять по образцу предыдущей строки.
4. Прочитать строку обратно и сверить дату, часы, ставку и рассчитанную сумму.

### Проценты

**Заполненные часы не означают, что зарплатная таблица заполнена полностью.**
`Salary.fill` записывает только дату и часы. CLI пропускает уже заполненную
зарплатную строку и не начисляет проценты: этот блок всегда проверять отдельно.

В текущем листе: M4 — общий остаток задолженности, E в зарплатной строке —
сумма новой зарплаты, N:P — журнал процентов и дополнительных начислений.

1. Проверить, нет ли уже начисления за закрываемый месяц. Ориентироваться
   на дату, примечание и предыдущие строки; при наличии записи не добавлять дубль.
2. Получить **снимок базы до нового процента и без новой зарплаты**.
   Если зарплата за закрываемый месяц ещё не внесена, база равна текущему M4.
   Если уже внесена, база равна `M4 − E_новой_зарплатной_строки`.
   Предыдущие проценты уже входят в остаток: повторно их не вычитать.
3. Зафиксировать денежную базу с двумя знаками по образцу прежних записей.
   Ставка — **1% за месяц**. Не включать новую зарплату в базу.
4. В следующей пустой строке только блока N:P записать:
   N — дату заполнения; O — формулу с числовым снимком базы, например
   `=10000.00*0.01`; P — пояснение `10_000.00 * 0.01`.
   Это условный пример, не реальные суммы. Формат N:P скопировать из
   предыдущей процентной строки, не копируя всю строку листа.
5. **Не использовать `=M4*0.01` в O:** M4 включает `SUM(O:O)`, получится цикл.
   Старые проценты не пересчитывать по сегодняшнему остатку. При повторной
   проверке уже добавленного процента пользоваться сохранённым снимком базы;
   текущее M4 уже включает новое начисление и может включать поздние платежи.
6. Сохранить принятую в таблице точность формулы; отображение — два знака.
   Прочитать дату, формулу, сумму и пояснение обратно. Убедиться, что общий
   остаток вырос ровно на начисление, а остальные значения и формулы сохранены.

Базу, расчёт и результаты проверки хранить в `private/` рядом с черновиками
и резервными копиями. Реальные финансовые суммы в публичную инструкцию не добавлять.

### Месячный текст и завершение

Месячный текст брать из шаблона `month_report` в `config.yml`, часы — точные,
до секунд, без зарплатного округления. Фразу «Расчёт зарплаты уже в таблице»
использовать только после проверки **и зарплатной строки, и процентов**.
Выдать месячный текст отдельным копируемым блоком вместе с ежедневным сообщением.

Проверить каждую часть независимо: документ, подготовленный/отправленный
чат, таблицу времени, зарплату и проценты при закрытии месяца, локальные
CSV/YAML, журнал, старые records и БД. `document` и `sheet` ставить только
после проверенной записи; `sent` — после фактической отправки.

При сетевом сбое после записи сначала прочитать фактическое состояние.
Не повторять вслепую вставку строк или начисление процентов. Готовые файлы
и черновики не равны внешней записи. Git push и отправка в чат
не входят в сохранение дневника и выполняются по отдельному поручению.
